# ADR 0008: pnpm como gestor de paquetes

- **Estado:** Aceptado
- **Fecha:** 2026-11-06

## Contexto

El proyecto usaba npm con `package-lock.json`. El autor prefiere pnpm: instala más rápido, comparte un almacén global entre proyectos y su `node_modules` estricto evita usar dependencias que no están declaradas en `package.json`.

Había que cambiar sin mover versiones y sin romper los scripts `pre`/`post` (`prebuild` regenera el árbol de docs y `postbuild` indexa con Pagefind).

## Decisión

- pnpm 10 es el gestor del proyecto, fijado en `package.json` con `"packageManager": "pnpm@10.33.0"`. Con `corepack enable` se usa esa versión exacta.
- `pnpm-lock.yaml` se generó con `pnpm import` a partir de `package-lock.json`, así que las versiones resueltas son las mismas. `package-lock.json` se elimina.
- Los scripts llaman a pnpm (`predev` y `prebuild`: `pnpm docs:tree`) y la documentación usa `pnpm <script>` y `pnpm astro …` en lugar de `npm run` y `npx astro`.
- Prettier ignora `pnpm-lock.yaml`, como antes ignoraba `package-lock.json`.

## Consecuencias

- `pnpm build` ejecuta `prebuild` y `postbuild` igual que npm (comprobado: árbol de docs, 11 páginas y el índice de Pagefind).
- pnpm 10 bloquea por defecto los scripts de instalación de las dependencias. Hoy no hace falta ninguno (`esbuild` y `sharp` traen sus binarios como dependencias opcionales). Si una dependencia nueva lo necesita, se autoriza con `pnpm approve-builds`.
- Quien clone el repo necesita pnpm: `corepack enable` y después `pnpm install`.
- Los ADR anteriores siguen citando `npm run …`: describen el proyecto tal como era al escribirlos.
